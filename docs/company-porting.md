# 회사 버전에 무엇을 가져갈까

**전제:** 이 저장소를 회사에 주는 것이 아니다. 저장소 소유자가 여기서 **유용한 것만 직접 골라** 회사용 별도 저장소를 새로 만든다. 회사에는 설명할 수 있는 내용만 있으면 되고, 나머지는 개인 자산으로 계속 강화한다. 목적은 회사에 비전을 공유하고 피드백을 받아 이 개인 프로젝트를 키우는 것이다.

이 문서는 그 추출을 쉽게 하려는 분석이다. 이 저장소의 코드와 기록을 근거로 했고 회사 버전 코드·환경은 확인하지 않았다. 그래서 "무엇을 어디서 자르면 독립적으로 동작하는가"에 집중한다.

## 한 줄 결론

> **회사에는 "SSO 연결 진단 + 읽기 작업 1개"의 수직 단면과 인증 흐름도 한 장만 공유한다.** 기존 사내 웹 인증은 유지하고, 인증·사용자 격리·고정 조회라는 설계 원리를 설명한다. 리포트·EOS·Config 집계·런북·예약 동기화는 개인 프로젝트 영역으로 둔다.

## 가져갈 것 (설명 가능한 최소 단면)

```text
기존 사내 웹 인증은 유지
        ↓
서버에 등록된 AWS 연결 선택
        ↓
사용자 전용 worker에서 Device Code 로그인
        ↓
접속 계정·역할 확인 (STS)
        ↓
EC2 목록 같은 읽기 작업 1개
        ↓
성공 / 권한 부족 / 세션 만료 / 조회 실패 표시
```

| 가져갈 설명 | 근거 코드·문서 | 이유 |
|---|---|---|
| 인증 흐름도 | [`architecture/auth-flow.md`](architecture/auth-flow.md) · `auth-flow.svg` | 동료가 가장 먼저 묻는 "웹 로그인과 AWS 로그인은 어떻게 다른가"에 한 장으로 답함 |
| Device Code 로그인 명령 구성 | `packages/worker-protocol/cli-contract.ts` | `--use-device-code --no-browser`, 고정 SSO 설정, 인증 URL 검증 |
| 사용자 전용 실행 환경 | `apps/worker/src/cli-runtime.ts` | 전용 홈·캐시, 권한 `0700/0600`, 심볼릭 링크 검사, 자격증명 환경변수·인스턴스 역할 차단 |
| 연결 상태 관리 | `apps/worker/src/cli-worker.ts` | 시작 → 승인 대기 → STS 확인 → 연결/만료/실패 |
| 신원 확인 | `checkedCliIdentity()` | 로그인 성공과 의도한 계정·역할 접속을 분리 |
| 결과 표시 | 오류 코드 분류(`bounded-process.ts`) | 권한 부족·만료·조회 실패를 구분해 보여 줌 |

여기에 **테스트가 있는 작은 예제** 하나를 붙인다. Claude Code로 확장하는 방법도 같이 보여 준다.

> "인증·권한·격리 코드는 유지하고, 허용된 읽기 함수 하나를 추가한 뒤 테스트를 통과시키는 방식으로 확장해 보세요."

처음에는 코드로 동작이 정해진 쉬운 자동화를 보여 주고, 팀이 스스로 개선하게 하는 방향과 맞는다.

## 직접 떼어 내기 가이드

범위는 두 단계다. 의존 범위는 `node scripts/ops/slice-closure.mjs <진입 파일...>`로 다시 계산할 수 있다(읽기 전용, 소스만 읽음).

| 단계 | 진입 파일 | 파일 수·줄 수 | 외부 의존성 | 내용 |
|---|---|---|---|---|
| **1. 인증 핵심** | `packages/worker-protocol/cli-contract.ts`, `bounded-process.ts`, `apps/worker/src/cli-runtime.ts` | 8개, 약 580줄 | `zod`와 Node 내장 모듈뿐 | 고정 SSO 설정·명령 생성, STS 신원 검사, 사용자 전용 실행 환경, 제한된 프로세스 실행 |
| **2. 연결 상태 기계** | 위에 `apps/worker/src/cli-worker.ts` 추가 | 14개, 약 1,410줄 | 같음 | 로그인 시작 → 승인 대기 → STS 확인 → 연결·만료·실패 관리. 동기화·디렉터리·버전 읽기 코드가 딸려 와서 줄여 써야 함 |

1단계 8개 파일은 임시 폴더에 이 파일들과 `zod`만 두고 확인했다. 타입 검사가 깨끗하고, 로그인 명령 생성(`sso login --use-device-code --no-browser`)과 동일인 검사(같은 사용자 통과, 다른 사용자 `web_identity_mismatch`)가 동작했다.

**1단계 파일 목록**

```text
apps/worker/src/cli-runtime.ts              사용자 전용 디렉터리·환경변수 격리, CLI 실행
packages/worker-protocol/cli-contract.ts    binding·명령 생성·STS 검사
packages/worker-protocol/bounded-process.ts 시간·출력 제한 프로세스, AWS 오류 이름 분류
packages/contracts/errors.ts                오류 타입
packages/contracts/access-context.ts        검증된 호출자 문맥 타입
packages/contracts/aws/connections.ts       연결 상태 형식
packages/contracts/aws/directory.ts         (cli-contract가 참조, 줄여도 됨)
packages/contracts/aws/runbooks.ts          (cli-contract가 참조, 줄여도 됨)
```

**줄여서 가져갈 곳.** `cli-contract.ts`에는 런북·디렉터리·읽기 작업(`CliOperation`) 명령 생성이 같이 들어 있다. 설명용 단면이면 `identity`, `login`, `logout`과 읽기 작업 1개만 남기고, 나머지 연산과 그에 딸린 `runbooks.ts`·`directory.ts`를 지우면 `zod`와 몇 개 파일만 남는다. 지운 뒤 타입 검사가 통과하는지 확인한다.

**함께 가져갈 테스트.**

| 테스트 | 상태 |
|---|---|
| `tests/unit/worker/login-name-match.test.ts` | 1단계 파일만 사용(그대로 이식 가능). 동일인 검사 |
| `tests/unit/worker/cli.test.ts` | 2단계 파일이 필요. 로그인·STS·격리·제한 프로세스 전체를 다루는 기준 테스트라 가장 설명 가치가 큼 |
| `tests/unit/host/oidc-verifier.test.ts` | 웹 검증기(회사에 이미 웹 인증이 있으면 제외) |
| `tests/unit/worker/{sync,reads,directory-reads,runbooks}.test.ts` | 제외 범위의 기능 |

**추출 점검표.**
1. 새 저장소는 새 `git init`으로 시작한다. 이 저장소의 이력·`docs/`·`.data/`를 복사하지 않는다.
2. 코드 속 `example`·`synthetic` 값은 합성이지만, 가져갈 때 한 번 더 `grep`으로 실제 계정·URL이 없는지 확인한다.
3. 주석·파일 이름에 이 저장소의 다른 기능(예: 런북, Config 집계)을 가리키는 표현이 남지 않았는지 본다.
4. 출처와 라이선스는 새 저장소에서 정한다. 이 저장소에는 아직 라이선스가 없고 `docs/provenance/assets.md`도 새 공개 라이선스를 부여하지 않는다고 적고 있다. AWS 로고 같은 자산은 가져가지 않는다.
5. 예제는 읽기 작업 하나(예: EC2 목록)와 성공·권한 부족·세션 만료·조회 실패 표시까지만 둔다.

## 가져가지 않을 것

| 제외 | 이유 |
|---|---|
| 웹 SAML bridge·popup PKCE·ES256 verifier 전체 | 회사에는 이미 승인된 웹 인증이 있다고 가정. AWS 연결 경로만 설명하면 충분 |
| 운영 리포트·저장된 보기·EOS 센터·거버넌스 판정 | 설명 범위가 "인증 구현"에서 "운영 플랫폼 구축"으로 커짐 |
| AWS Config 집계자 모드, 다계정·다리전 동기화 | 회사 다계정 환경에서 검증하지 않았음 |
| 런북 실행(요청·승인·실행) | 쓰기 경로. 실계정 확인은 개인 테스트 계정 1건뿐이며 승인·감사 설계가 회사 정책에 의존 |
| 예약 동기화, 무인 수집 | 사람의 SSO 세션 기반이라 상시 자동화 인증(workload role)은 별도 설계 |
| 로컬 SQLite·DynamoDB adapter, 배포 스크립트 | 회사 운영 저장소·배포는 상대 파트의 결정 사항 |
| 실제 계정·조직·URL이 든 설정 | 어떤 형태로도 옮기지 않음(합성 값만) |

## 설명할 때 구분할 상태

| 항목 | 상태 | 말하는 법 |
|---|---|---|
| 웹 로그인 → Device Code → STS → 읽기 | 개인 테스트 Identity Center와 로컬 Docker에서 실제 확인 | "구현했고 개인 계정에서 확인했다" |
| 다계정·다리전 동기화 | 구현. 실제 접근 확인은 계정 1개 | "구현했지만 회사 다계정에서 검증하지 않았다" |
| 런북 실행 | 구현. 개인 계정에서 연결 점검 1건 성공(2026-10-11) | "쓰기 경로는 설명 예제에서 제외" |
| 회사 IdP·운영 저장소·TLS·Linux 호스트 격리 | 미검증 | "회사 환경 검증은 별도 과제" |

## 공유 전에 짚을 한계

1. **웹 사용자와 AWS 승인자의 동일성.** 서버 설정(`identityPolicy.requireLoginNameMatch`, 기본 꺼짐)으로 웹 로그인 이름과 AWS 세션 이름을 대조하는 검사를 구현했고 합성 테스트로 확인했다([자세히](architecture/auth-flow.md#아직-닫히지-않은-것-정직한-한계)). 회사의 두 이름이 같은 값이 아니면 매핑 규칙이 필요하다. 회사 환경에서 "웹 A, Device Code 승인 B" 시나리오를 검증하기 전에는 "동일인까지 검증한다"고 단정하지 않는다.
2. **사람의 세션과 상시 자동화는 다르다.** 예약 수집·공용 서비스는 별도 인증 설계가 필요하다.
3. **조회 범위.** "전체 자산 현황"이 아니라 "설정된 수집 범위의 현황"이다.
4. **쓰기 경로.** 설명 예제는 읽기 전용으로 한정하고, 런북은 구현·활성화·실검증 상태를 구분해서 말한다.

## 소유와 공유 경계

- 이 저장소는 개인 프로젝트이며 공개 저장소다. 회사 코드·설정·실제 관측 자료를 이 저장소로 가져오지 않고, 이 저장소의 실제 계정·토큰도 어디에도 넣지 않는다.
- 회사에는 이 저장소를 주지 않는다. 소유자가 위 가이드로 **설명 가능한 단면**(흐름도, 해당 코드 설명, 예제와 테스트)만 직접 골라 별도 저장소로 만든다. 구현 대행이나 운영 책임을 먼저 약속하지 않는다. 확장·배포의 주체는 받는 파트가 된다.
- 회사 업무와 겹치는 부분이 있을 수 있으므로, 공개 범위와 라이선스는 사내 규정을 확인한 뒤 정한다. 이 저장소에는 아직 라이선스 파일이 없고, `docs/provenance/assets.md`도 새 공개 라이선스를 부여하지 않는다고 적고 있다.
- 피드백은 개인 프로젝트 쪽으로 가져와 반영한다. 회사 내부 맥락(사람·팀·정책)은 이 저장소 문서에 적지 않는다.

## 공유 순서 제안

1. 흐름도 한 장으로 "두 로그인은 다른 질문"을 설명한다.
2. 추출한 `cli-contract.ts` → `cli-runtime.ts` → `cli-worker.ts` 순서로 코드를 보여 준다(위 표의 네 군데).
3. 읽기 작업 1개를 붙인 예제를 시연하고, 성공·권한 부족·만료 표시를 보여 준다.
4. 한계 4가지를 먼저 말하고 피드백을 받는다.
5. 받은 피드백은 `docs/NEXT_PLAN.md`에 반영해 개인 프로젝트를 강화한다.
